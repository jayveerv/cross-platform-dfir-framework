S5 is deliberately hard. (1) A legitimate session for the same user is open when the attacker logs in, and Linux auth.log has no session id, so a legitimate command is wrongly attributed to the attacker (a false positive). (2) An insider moves laterally from an internal IP without brute force, so no untrusted entity exists and the rules miss the incident (a false negative). These are the known limits of a rule-based design and the motivation for anomaly-based detection as future work.

Completeness = supported records normalized ÷ supported records present in the source. Precision/recall are computed per event against the generator's ground truth (which attack each record belongs to). False alerts = flagged events that are not part of any attack.

6. Limitations (state these honestly in the thesis)

  • All data is simulated (real log formats, generated events). Results show the framework works on these scenarios, not on production traffic.
  • Ground truth comes from the generator, so scenario difficulty is limited by what the generator produces.
  • Detection is rule-based (thresholds in config.py); novel attack patterns outside the rules are not flagged.
  • Linux session attribution is a heuristic (latest login of the same user on the same host).
  • Linking a Linux credential file to an AWS key requires the analyst-supplied credential inventory.
  • The custody ledger detects changes after the fact; it does not stop them. Removal of the last entries needs the anchor hash noted outside the case folder, and a fully rewritten chain is detected only when the ledger was HMAC-signed with a key the attacker does not have (row 'checked WITHOUT key or anchor' shows the plain hash chain alone misses it).
  • Scalability is measured for a single process; the largest test had 104,634 records.
